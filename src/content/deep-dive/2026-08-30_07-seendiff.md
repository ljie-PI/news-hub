# seendiff

## 事件背景

2026年8月29日，seendiff 以“带进度追踪的代码差异查看器”登陆 Product Hunt；冻结日榜记录为133票、6条评论。它瞄准的不是自动批准代码，而是编码代理一次生成大批改动后，人类仍需逐段读完、又容易忘记读到哪里的现实摩擦。官方 API 已按原始编号1231748核对同名发布；网页本轮受 Cloudflare 挑战页阻挡。

## 核心观点 / 产品机制

它是 MIT 许可的本地 Python/FastAPI 工具：调用 Git 生成相对基线的完整差异，在浏览器中虚拟化显示；代码块滚过视口自动记为 Seen，Reviewed 必须手动确认。源码显示进度存入本机 SQLite，以仓库、基线、分支及内容派生的块标识关联，因而能跨关闭、改写提交或变基保留。配套 skill 可让编码代理生成 JSON walkthrough，载入前校验文件与行号。服务仅绑定127.0.0.1并校验 Host，抓取远端也须显式开启；“无遥测、数据不出本机”仍属于项目方口径。本轮仓库抽查有36项测试通过。

## 社区热议与争议点

官方 GraphQL 当前返回4条顶层、4条回复，所有用户身份均被脱敏，故只能按内容举例：一位用户称经常忘记已审与待审部分，直接印证痛点；另一位看好让代理讲解其差异的 guided walkthrough；有人追问同一文件被代理多次修改时如何融入团队流程，未见回答；跨设备同步问题则得到产品方口径回复：数据全在本机，暂不自动同步，除非自行同步 SQLite。节点数与“6条评论”口径不等，本文仅视其为可见子图。

## 行业影响与未来展望

seendiff 把注意力管理置于“再加一个 AI reviewer”之前：价值是证明哪些代码已看、哪些明确签核，并让代理辅助解释而非替代判断。其局限也清楚：README 明示不做编辑、评论、合并或冲突解决；本地状态利于隐私，却削弱多人和多设备协作。若未来加入可审计同步，并避免“由写代码的代理自我解释”形成单一信任源，才更可能进入团队级审查链路。
