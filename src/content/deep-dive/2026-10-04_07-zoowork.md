# ZooWork

## 事件背景
ZooWork（原 ZooClaw）10月3日以“交付而非只构建 Agent”为主张发布，面向前线部署工程师与领域专家。批次冻结为284票、40评、日榜第一；本次官方 GraphQL 复核同一 post 1259794 时已变为285票、41评，热度不等于技术验证。

## 核心观点 / 产品机制
产品把自然语言 Builder 与 Managed Agent API 接到同一交付链：专家写角色、SOP、技能和完成标准，开发者可用 TypeScript、Python 或 HTTP 创建持久 Agent、Session 与事件流；模型及工具循环在隔离沙箱执行，结果可经链接、API、Slack 等交付。文档说明轨迹需由事件历史组装，质量 outcome 仍由应用侧保存；同一 Agent 的会话默认共享工作区，涉及客户文件隔离须每用户建一个 Agent。1—2秒冷启动、闲置不计费均为官方自报。

## 社区热议与争议点
独立评论中，Sophie 称已在黑客松用它原型化无人机巡检流程，肯定“从演示到运营”；Gal 担心非技术人员周二改流程、周三便破坏客户任务，Maker David 回应可在新会话测试、手动 Publish。Gene 指出 config_version 只是计数器、回滚留给应用；David 明确承认分阶段发布和一键回滚仍需向团队确认。Jeetendra 追问多客户隔离，Maker 说明共享同一 Agent 就共享沙箱，建议每客户单独建 Agent。这些回答揭示交付便利背后的版本治理与租户成本。

## 行业影响与未来展望
ZooWork 的差异点是把领域知识、托管运行时和分发渠道合为交付面，可能让 FDE 从“写原型”转向“运营服务”。但 API 仍标为 Developer Preview；若缺少原生回滚、渐进发布、独立 outcome 与低成本租户隔离，规模化维护会回到客户应用侧。公开 Demo 已能进入五步业务诊断表单，但不能替代生产可靠性评测。
