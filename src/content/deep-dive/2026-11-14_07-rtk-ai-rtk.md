# rtk-ai/rtk

## 定位与痛点剖析
RTK 是面向编码智能体的命令代理：在测试、差异、日志等输出进入上下文前压缩噪声，服务高频使用终端工具、受上下文和费用约束的开发者。其目标不是减少模型推理，而是缩小工具结果；README 所称“最高减少九成命令输出、覆盖百余命令、单次低于二十五毫秒”均属项目自报，不能等同账单降幅。

## 核心架构与技术细节
代理钩子先把可识别的 shell 调用改写为 `rtk` 子命令，Rust 主程序再按生态路由到底层命令，以统计提取、错误保留、分组、截断和去重处理输出，并透传退出码；被删内容可由 `recall` 找回，SQLite 记录收益。源码以 `bytes/4` 向上取整估算 token，因此压缩百分比实为字节比，绝对 token 及费用都只是近似。本次复跑 `cargo test --workspace` 全绿。默认二进制把 Apache-2.0 的 CLI、钩子和过滤器与 BUSL-1.1 引擎链接；纯 Apache 版不含引擎，代理也属 BUSL。附加授权允许免费生产使用，但禁止将引擎或衍生物作为付费、托管服务，二〇三〇年九月九日转 Apache-2.0。

## 竞品对比与生态站位
直接竞品 Snip 以 Go 和声明式 YAML 过滤器换取更易扩展、MIT 许可；Headroom 则用本地内容路由、代码解析与文本模型覆盖文件、历史和检索结果，范围更广但部署更重。RTK 的优势是成熟命令专用过滤、跨智能体钩子、恢复与统计一体化；短板是启发式改写只覆盖可触达表面，端到端收益取决于智能体行为。

## 开发者反馈与局限性
开放 issue #5110 报告循环体命令漏改写，#5107 报告沙箱不可写时截断却丢失恢复提示，#5078 更指出直接把过滤结果重定向可生成残缺 JSON。独立 issue #5087 的八十次实验虽全部解题，单位解题成本却比基线高三成六，原因包括频繁 `bypass` 与额外轮次；JetBrains 配对评测也测得低推理档成本中位数增加百分之七点六，高档基本持平。可见“输出更短”不自动推出“总费用更低”。
