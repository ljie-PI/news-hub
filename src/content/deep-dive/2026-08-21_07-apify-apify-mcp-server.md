# apify/apify-mcp-server

## 定位与痛点剖析
它是 Apify 平台与 MCP 客户端之间的适配层，让外部智能体、编辑器和命令行代理把 Actor 当工具使用。它针对的痛点是：代理若要跨社媒、地图、电商与搜索站点取数，往往需逐站开发抓取器，并自行处理输入模式、运行状态和结果存储。这里把流程收束为发现 Actor、读取模式、执行、分页取回数据。README 以项目方口径称可接入八千多个 Actor；远端支持 OAuth，本地可走 stdio。

## 核心架构与技术细节
项目以 TypeScript、Node.js 22 和 MCP SDK 构建，`ActorsMcpServer` 门面共享 Apify 客户端、工具注册、支付与遥测核心；其下并列保留面向旧协议的有状态适配器，以及每请求创建实例的新无状态适配器，避免并发请求污染共享状态。工具加载分为异步获取 Actor 元数据、按客户端能力同步选定普通或组件化工具两阶段。Actor 输入模式经裁剪后转成工具定义，运行只返回存储标识与下一步，再自动注入数据集读取等工具，控制上下文体积。公开仓库是核心包，托管站的鉴权、限流和多节点层位于私有仓库。

## 竞品对比与生态站位
Firecrawl MCP 和 Bright Data MCP 更聚焦网页搜索、抓取与公共网络访问；本项目的差异是借 Actor Store 覆盖抓取、自动化、任务、存储及代理内支付，并能动态发现新工具。代价是执行、计费与数据面深度绑定 Apify，Actor 品质也并不一致；所谓开源主要覆盖协议核心，而非完整托管栈。

## 开发者反馈与局限性
GitHub REST 快照显示仓库有 4392 星、232 个分叉及 135 个开放条目。近期 issue 暴露了真实边界：#1289 尚在验证带点号的工具名能否兼容 Claude 客户端；#1287 指出新任务工具只有单元测试、缺真实接口集成覆盖；#1290 认为错误请求被误导去报故障。开放 PR #1275 正尝试在输入校验失败时返回实际模式。另有默认开启遥测、官方文档写 Node.js 18 而包清单要求 22 的文档漂移，以及每用户每秒三十请求限制。
