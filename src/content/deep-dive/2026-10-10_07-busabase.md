# Busabase

## 事件背景

Busabase 于 10 月 9 日登上 Product Hunt 日榜第二；批次冻结为 256 票、67 条评论。团队把痛点定义为：不同 Agent 的成果散落在聊天、文件与各自工具中，下一次任务又得重建上下文。不过“通用记录系统”及客户成效目前主要是厂商定位，并非独立验证。

## 核心观点 / 产品机制

它没有内置模型，而把 Base、文档、文件、Skill 与 AirApp 作为共享节点，经 Agent Skill、MCP、OpenAPI 或 CLI 接入 Claude Code、Codex 等。写入先形成带作者、字段差异和历史的 Change Request；权限决定立即合并还是进入 Inbox 审核，提案级凭证只能提交。公开仓库显示桌面版用 PGlite、本地文件存储且单工作区免登录，云版才提供多人权限；交互 Demo 确实展示了变更前后、来源与评审状态，但只读样例不能证明生产可靠性。

## 社区热议与争议点

官方 GraphQL 分三页取得 23 条顶层评论与 39 条回复，共 62 个可见节点，少于冻结总数，且身份被脱敏。具体讨论中：一位用户认可变更前后对照，认为真实业务数据需要审核；一位开发者反驳工程上下文本就应留在 Git，团队也承认 Busabase 更偏业务协作；另有用户追问错误事实污染下游，产品方澄清只有 `changeRequest` 权限才会真正阻断，`write` 可直接合并；细粒度权限讨论则暴露目前只能按 Space 或 Base 等节点隔离，筛选视图不是行级安全规则。另有公开 Issue 记录 Windows 启动故障，维护者虽发布修复，也坦言尚未在 Windows 实机验证且 CI 未覆盖主启动命令。

## 行业影响与未来展望

它试图把“Agent 记忆”升级为多人可审计的业务事实层，价值在跨 Agent 复用与责任链，而非更强召回。机会在 CRM、内容、研究等低频关键写入；风险是权限配错仍会直写、审核队列制造延迟，且开源版的单工作区边界限制团队治理。能否成为记录系统，最终取决于冲突处理、权限测试与真实团队持续审核，而不是榜单热度。
