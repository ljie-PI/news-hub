# You said no MCP

## 事件背景

Earendil 曾把“不支持 MCP”当作 Pi 的鲜明立场，却在 9 月 29 日宣布将其纳入核心。批次冻结时热度为 580 points、329 comments。转向不只是因为协议一年间有所改进，也因为 Pi 为新模型补齐延迟加载工具、会话中系统消息等能力时，发现 MCP 所需的解释器与元数据改造对整个工具系统都有价值。

## 核心观点 / 产品机制

Pi 的 Codemode 是运行在代理循环一侧的 JavaScript 沙箱：模型可在其中排序、组合 MCP 工具调用，状态留在会话记录而非文件系统；小型 JavaScript 运行时还能以 WASM 分发。工具可标为延迟加载或仅供 Codemode 使用，配合文档发现与结构化返回，减少把全部工具定义和文本结果塞进上下文。作者仍承认 MCP 难以组合，服务器生态的返回格式和设计习惯尚未统一。

## 社区热议与争议点

本次 Algolia 实取 100 个可见节点，已触及抓取上限。支持者 _fw 将 MCP 比作并不完美却因兼容性胜出的 USB-C，认为统一生态优于多套“最优”接口；反方 skohan 指出原有扩展已能工作，担心核心集成破坏 Pi 的极简定位。mikeocool 认为 OpenAPI、OAuth 与方法发现本可完成同样任务，MCP 是重复造标准；另一条讨论中，ppsreejith 追问文件上传，rcarmo 称企业实践仍常靠带外存储句柄或链接，暴露协议边界未收敛。

## 行业影响与未来展望

这次转向说明代理工具竞争正从“是否支持协议”转向“如何发现、组合并隔离工具”。Pi 用沙箱吸收 MCP，而非直接铺满工具表，可能推动小型代理框架兼容标准；但成败仍取决于服务器能否提供结构化数据、附件传输与清晰权限边界，否则核心化只会把生态碎片带进框架。
